# summer-trie 优化报告

> 本轮对 `summer-trie`（面向线路资源类缓存场景的前缀树组件）的系统优化总结，覆盖**并发正确性、查询性能、内存占用、可观测基准**四方面，全部带测试与数据验证。
>
> 度量环境：JDK 8，单机；规模 N = 100,000 条记录；内存用 JOL `GraphLayout.totalSize()`，吞吐用 JMH（1 fork × 3 轮，吞吐误差带较宽但数量级结论稳健，`gc.alloc.rate.norm` 字节/op 稳定可信）。

## 二、并发与正确性

| 项 | 问题 | 修复 |
| --- | --- | --- |
| A1 `putChild` | check-then-act，并发插同 key 各自 new 节点互相覆盖，丢整棵子树 | 改 `children.computeIfAbsent`，并发节点原子 |
| A2 字典计数 | `getOrDefault + put` 非原子，并发算错 | `counter.merge` / `computeIfPresent` |
| A3 自增 key | `containsFieldValue` 后 `nextKey()` 非原子，同值并发分两个 key、字典/索引/计数错乱 | 新增 `Dict.getOrCreateNodeKey`，用 `indexer.computeIfAbsent` 原子分配 |
| A4 insert | 中间层字段为 null 抛异常，前几层已落树 → 悬挂路径 | 整行预校验非空，全非空才落树 |
| 尾层漏数据 | `dfsSearch` 尾层只取首个 entry 即 `return` | 展示字段遍历全部兄弟、仅过滤字段去重一行 |
| normErase 残留 | 非叶层条件删空子树时只删 `search` 过滤副本，真实树节点残留 → `dataSearch` 返回一串 null | 完全删空时从真实节点 `removeChild`；共享字典 key 仍交 `counter`，不误删其它父节点在用的编码 |

**并发回归护栏** `TrieConcurrencyTest`：8 线程 × 高度重叠 key 并发插入，断言无丢子树、字典无重复 key、读写并发无异常。`subtreeSize` 用 `volatile int + AtomicIntegerFieldUpdater` 原子维护（无每节点额外对象开销）——正是被该测试抓出"非原子增量丢更新"后改的。

## 三、查询与计数

- **`dfsSearch` 回溯**：原先每个节点 `new ArrayList<>(path)` 复制整条路径；改为回溯（进分支压栈、递归返回弹栈），仅在产出结果行时快照。消除所有不产出结果的中间节点复制。
- **`subtreeSize` + `getSize` O(1)**：每节点维护"子树记录数"；`getSize` 可靠时直读根节点 O(1)，`fastErase` 会置不可靠并退化为遍历兜底（结果仍正确）。
- **新增 `count(Criteria)`**：下钻到条件最深层，累加命中节点的 `subtreeSize`，**不物化对象**；不可靠时按子树遍历兜底。

**JMH 实测**

| 基准 | 吞吐 (ops/ms) | 分配 (B/op) |
| --- | --- | --- |
| `getSize` O(1) | ~690,000 | ~0 |
| `getSize` 遍历(对照) | ~5 | 170,104 |
| `count` | ~49 | 47,855 |
| `dataSearch().size()`(对照) | ~20 | 91,685 |

### `limit` 下推（命中即停，避免全量物化）

`Criteria.limit(n)` 把结果上限随查询**下推到遍历过程**：采集满 n 条立即终止，不再"全量物化后由调用方截断"。两条路径：

- `dataSearch` / `propertySearch`（经 `levelSearch`）：去重采集到 n 个 key 即停（迭代器手动拉取支持提前结束）。
- `listSearch` / `treeSearch` / `queryAsTreeNode`（经 `dfsSearch`）：`result.size() >= n` 时逐层短路、终止递归。
- **未设 `limit` 的路径保持原逻辑、零回退**；`limit` 是查询级属性、链式任意节点设置都生效、非法值（≤0）抛异常。

**JMH（N=10万，宽查询 `cabinClass=ECON` ≈2.5万命中；`gc.alloc.rate.norm` 字节/op 稳定可信）**

| 基准 | 吞吐 (ops/ms) | 分配 (B/op) |
| --- | --- | --- |
| `dataSearch` 全量(对照) | 0.20 | 2,001,923 |
| `dataSearch` limit=10 | 14.7 | **96,552（−95%）** |
| `treeSearch` 全量(对照) | 0.14 | 2,028,116 |
| `treeSearch` limit=10 | 1147 | **2,648（−99.9%）** |

> `dfsSearch` 路径（tree/list）是硬提前终止，省得最彻底（−99.9%）；`levelSearch` 路径（data）靠惰性流提前结束，也省 −95%。

### 查询热路径去 Stream churn（P1）

常规（无 `limit`）查询逐层下钻原先用 `Stream.of(node).flatMap(...).anyMatch(...)` 管道，每访问一个中间层节点都新建一组 Stream 中间对象（阶段对象 / Spliterator / lambda 闭包），在「宽展示 + 深过滤」场景下是查询热路径的 GC churn 重灾区。

- **`childrenAnyMatch`**：改显式 `for` 遍历子节点 + 命中即 `return true`，消除每节点的 Stream 中间对象。
- **`levelSearch` 按 `limit` 分派**：`levelSearchAll`（无 `limit`·全程显式遍历去 churn）/ `levelSearchLimited`（带 `limit`·**保留惰性 Stream**——否则 `limit` 下推会退化为全量下钻、抵消上一节收益）。
- 纯等价重构，结果集逐一致；全部单元测试回归全绿（含 `TrieLimitTest` 8 个 `limit` 正确性用例，确认惰性 `limit` 路径未被破坏）。

**JMH 前后对照（N=10万，`gc.alloc.rate.norm` 字节/op）**

| 基准 (B/op) | 优化前 | 优化后 | Δ |
| --- | --- | --- | --- |
| `anyMatch_broad`（宽展示+深过滤） | 712,293 | **182,624** | **−74.4%** |
| `anyMatch_narrow` | 3,790 | **2,670** | −29.6% |
| `simple`（展示层 eq） | 50,425 | **45,758** | −9.3% |

> `childrenAnyMatch` 的 churn 是大头（约 −530KB/op）；`simple` 仅降 9% 印证「展示层 eq 的剩余分配主要在每层 `newChildren` 命中项拷贝（中间层免拷贝 T3 的地盘），而非 Stream」。

## 四、内存

| 阶段 | 内存 | B/记录 | 类型 |
| --- | --- | --- | --- |
| 原始(全 ConcurrentHashMap) | 43.37 MB | 433 | — |
| + LeafNode（空叶子不分配 map） | 36.17 MB | 361 | 零配置 |
| + counter 精简 | 31.92 MB | 319 | 零配置 |
| + AdaptiveNode（自适应节点） | 28.05 MB | 280 | opt-in |
| + ArrayDict（密集 key 数组字典） | **24.33 MB** | **243** | opt-in |

### 各项说明
- **LeafNode**：原先每个叶子（一条记录的终点）都挂一个空 `ConcurrentHashMap`（约 64B），10 万叶子≈6.4MB 纯浪费。新增无容器叶子节点（`children()` 返回共享 `emptyMap`、`subtreeSize()≡1`）。**零配置、并发安全、自动生效。**
- **counter 精简**：`HashMapDict` 的 `counter` 仅服务 `removeDictIfNonCount`（默认 `false` 且无 setter），且 size 已由 `subtreeSize` 维护——是纯死重。改为按需分配，默认不再维护。**零配置生效。**
- **AdaptiveNode / `ADAPTIVE_HASH`**：借鉴 ART"按扇出自适应"思想——低扇出用两条并行数组紧凑存储、高扇出升级 `HashMap`；`children()` 返回轻量 Map 视图，使现有面向 Map 的查询算子**零改动**。**opt-in（构建期写 + 只读/重建语义，非线程安全）。**
- **ArrayDict**：AutoMapping 的 nodeKey 是密集自增 id（1..N），用可增长数组按下标存 `id→对象`，省掉每条 `HashMap$Node`（约 32B）与装箱 Long key；保留 `indexer`（对象→id）用于插入去重与反查。经 AutoMapping **现有 `Dict` 构造函数 opt-in**，零侵入。
- **OneWayMapping 关 indexer**：`OneWayMapping` 正向用函数算 nodeKey、反向用 `dict`、`erase` 用函数，**从不读 `indexer`**——它被 `put` 填满却是死重。`HashMapDict` 加 `maintainIndexer` 开关（默认 `true` 兼容），`OneWayMapping` 默认建无 `indexer` 字典。**零风险、零依赖、不挑 fastErase/live-update**，正中「数据叶子用 OneWayMapping」的典型用法。JOL：OneWay 数据叶子 10 万条 **237 → 194 B/记录，−17.9%**。

### 分层落地建议
- **零配置层（LeafNode + counter 精简）**：并发安全、自动生效。现有 CHM 配置直接拿到 **433 → 319 B/记录（−26.4%）**，零风险、无需改任何代码。
- **opt-in 层（AdaptiveNode + ArrayDict）**：再到 **243 B/记录（−43.9%）**。适用于"启动构建 + 定期重建 + 运行期只读"（双缓冲定期重建正是此模式）。需并发增量写的字段请继续用 `CONCURRENT_*` 节点 + `HashMapDict`。
- **OneWayMapping 字段（关 indexer）**：已设为默认行为（OneWay 本就不读 indexer），无需改代码即生效、且不挑 fastErase/live-update；数据叶子为 OneWayMapping 的场景自动受益约 **−18%**。
- **一键收口（`Configuration.compactReadOnly`）**：把上面 opt-in 层的两项（AdaptiveNode + ArrayDict）收成**一个配置开关**。`setCompactReadOnly(true)` 后：哈希层节点（`HASH_MAP`/`CONCURRENT_HASH_MAP`）在 `DefaultNodeManager.createNewNode` 透明重映射为 `ADAPTIVE_HASH`（算子仍按原 nodeType 走、`children()` 是 Map 视图，零改）；AutoMapping 的默认 `HashMapDict` 在 `MapTrie` 构建前替换为 `ArrayDict`（用户自传字典不动）。效果等价手动配 **243 B/记录（−43.9%）**，但调用方**不改任何 per-property NodeType，只加一行**。语义为"构建期单线程写 + 运行期只读/定期重建"，非线程安全。纯重建型缓存开启即拿满收益、零风险；有 live update 的缓存暂不开或改「标脏 + 重建」后再开。

## 六、刻意未做 / 后续建议

- **T3（查询中间层免拷贝）**：拷贝点在 `BasicOperates` 每个过滤算子的 `newChildren()`——`search()→operate()` 每访问一个中间层节点就新建一个结果 map，而 `childrenAnyMatch→contains` / `levelSearchAll` 等只遍历一次即丢；P1 后 `simple` 路径仅降 9%，剩余分配主要在此。**风险**：`slice()` 会 `setChildren(search(...))` 把过滤结果写回真实节点、`remove` / normErase 也依赖「拷贝是独立副本」，故 T3 必须严格限定只读路径；返回视图还会破坏「每查询独占副本」与并发写的隔离，仅在「构建期写 + 运行期只读/重建」模型下安全。两档可选：① 低风险窄切片——给 `contains` / `childrenAnyMatch` 存在性判定加 `containsKey` 快路径（EQ/IN 单值），根本不建 map；② 广义视图/谓词迭代——高风险、须 JMH 证收益。**当前刻意缓做**。
- **AdaptiveNode 速度**：本数据扇出低，查询速度几乎无损；若某层扇出常年在 16~64，可调低阈值（更早升级 HashMap）或改"有序数组 + 二分"（需 Comparable key）。
- **ArrayDict 适用边界**：删除用 tombstone、id 不复用，"长期高频 erase+insert 增量更新"会让数组持续增长 → 这类场景用 `HashMapDict`。
- **业务侧建议**：双缓冲切换的 trie 引用字段加 `volatile`/`AtomicReference`（切换可见性保证，1 行，属业务侧改动）。
- **`indexer` 进一步压缩**：OneWay 已关 indexer（最大头）。剩 AutoMapping 高基数字段的 indexer 若需再压，可换 `IdentityHashMap`（仅恒等映射字段）或 fastutil `Object2LongOpenHashMap`（需加依赖）；城市码等低基数字段不值得动。
- **低优先技术债**：收紧泛型减少 raw types、`EMPTY_NODE` 全局单例隐患、注册表用 `HashMap`（启动期注册，影响小）。
